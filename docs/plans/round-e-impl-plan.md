# Round-E implementation plan

Measurement plan for what PR #26 (round-d) shipped but did not behaviorally
verify. Round-d's narrow rerun validated the 8 Phase 2 edits; the **post-run**
work (18 rubric corrections + 6 skill refinements + bundled-script CLI
examples) was applied *after* the rerun and is not yet behaviorally measured.

The starting state is **after PR #26 merges to `master`** (this plan ships
in that PR). Phases are sequenced narrow-to-wide; each phase is a decision
gate for whether the next runs.

Empirical record from round-d:
[`spyglass-skill-workspace/runs/round-d-2026-04-30/findings.md`](https://github.com/edeno/spyglass-skill-workspace/blob/main/runs/round-d-2026-04-30/findings.md).

## Open questions round-E should answer

1. **Did the 18 rubric corrections lift scores on the 8 corrected evals?**
   The corrections were applied post-run; round-d's headline (ws full-pass
   7/16, expectation rate 87.8%) was measured against the *old* rubric. A
   re-grade isolates rubric-correction impact from skill-content impact.

2. **Did the new bundled-script CLI examples convert "reads directive" into
   "executes script"?** Round-d's `code_graph.py` expected-vs-called recall
   was 8.3% (1/12, per
   [`script_call_confusion.csv`](https://github.com/edeno/spyglass-skill-workspace/blob/main/runs/round-d-2026-04-30/summary/data/script_call_confusion.csv)).
   Targeted via copy-pasteable command surfaces in `datajoint_api.md §
   Field Ownership`, `destructive_operations.md § Slot 4`, and
   `group_tables.md § Semantic subsets`.

3. **Does the "semantic-label → concrete-key" template fix eval-108-class
   gaps?** Round-d found eval-108 `right_ref_no_verify`: skill loaded
   `SortedSpikesGroup` but punted on deriving hippocampal sort_group_ids.
   The new 5-step pattern + negative rule in `group_tables.md` and the
   polymer-probe FK-walk caveat in `spikesorting_v1_pipeline.md` target
   this specific failure mode.

4. **Is `destructive_operations.md` content-bottlenecked or routing-OK?**
   Round-d found 1/5 pass-rate-when-loaded (per
   [`reference_effectiveness.csv`](https://github.com/edeno/spyglass-skill-workspace/blob/main/runs/round-d-2026-04-30/summary/data/reference_effectiveness.csv)).
   Routing finds the reference; the reference's content doesn't always
   deliver. Audit needed before the next sweep.

5. **What is the round-d-corrected headline number on a representative
   slice?** Round-d's narrow rerun was Phase-2-driven. A full sweep
   answers headline impact + regression questions; the narrow rerun
   answers whether specific fixes worked. Sequence the full sweep
   *after* the narrow checks confirm the fixes work.

## Phase E.1 — Re-grade round-d transcripts against corrected rubric

**Goal**: Isolate rubric-correction impact from skill-content impact. Cheapest
measurement available; reuses existing artifacts.

**Reuse**: 32 `response.md` files at
`runs/round-d-2026-04-30/iteration-1/eval-NNN-*/<condition>/outputs/response.md`,
plus 32 `grading.json` and 32 `expectations.json` files at
`runs/round-d-2026-04-30/iteration-1/eval-NNN-*/<condition>/`, plus 32
transcripts under `runs/round-d-2026-04-30/transcripts_snapshot/`. No
re-dispatch needed.

**Re-run only the grader phase** with the corrected `evals.json`:

```bash
# Per-eval grader subagents read the same response.md + transcript,
# apply the new expectations.json (regenerated by flatten_expectations.py
# from the corrected assertions), write a new grading.json into
# runs/round-d-2026-05-XX/iteration-1/.
```

**Estimated cost**: ~$15, 32 grader dispatches in parallel, ~10 min
wall-clock.

**Success criteria** (per-eval predictions from round-d's findings.md
"Post-run rubric corrections" section):

| Eval | round-d (old rubric) | round-e re-grade target (new rubric) |
|---|---|---|
| 028 | ws 9/13 (69%) | ws ~12/13 (~92%) — relaxed FK-walk-leads check + dropped `limit=1` substring |
| 089 | ws 7/10 (70%) | ws ~10/10 (100%) — removed `& (` literal substring + scoped multi-table-`*` check to 3+ tables |

Aggregated targets:

- Headline ws full-pass count rises from **7/16 to ~10/16** if 028, 089, and
  105 re-grade to full-pass; 041 (8/9) and 087 (14/15) improve expectation
  rates but likely remain partial under the split assertions; 118 stays
  partial because of the real qualitative-direction content gap; 085 and

**If the re-grade does not move these numbers**: the rubric-friction
hypothesis was wrong. Investigate per-eval before proceeding.

## Phase E.2 — Narrow rerun for behavioral changes

**Goal**: Measure whether the 6 post-run skill refinements + the bundled-script
CLI examples changed agent behavior. Re-grading existing transcripts can't
answer this — it requires fresh dispatches that pick up the updated skill.

**Subset selection**: 8 evals targeted at specific refinements, not the
full round-d 16. (Optional additions if budget permits: round-d evals 029
and 072 as additional regression checks on saturated ties; 100 to verify
the +29pp bs lift held; 088 / 113 to verify destructive-ops behaviors.
Default plan runs the 8 below.)

| Eval | What it tests |
|---|---|
| 089 | Sub-restriction-as-canonical (datajoint_api.md) + script execution |
| 108 | Semantic-label → concrete-key template (group_tables.md) |
| 028 | Polymer-probe FK-walk (spikesorting_v1_pipeline.md) + script execution |
| 105 | "Lead with working query, not # WRONG" framing (SKILL.md field-ownership) |
| 118 | Slot 5 qualitative direction (destructive_operations.md cascade template) |
| 087 | Slot 5 qualitative direction (cascade template, second instance) |
| 107 | Regression check: skill-only win at 12/12 in round-d, must hold |
| 041 | Regression check: skill-only win at 7/8 in round-d, must hold or lift |

**Estimated cost**: depends on ws-only vs. ws+bs choice (see "ws-only vs.
ws+bs question" below):

- ws-only on 8 evals: 8 dispatches, ~$8-10, ~15 min wall-clock.
- ws+bs on 8 evals: 16 dispatches, ~$15-20, ~30 min wall-clock.
- ws-only on 8+ evals (optional additions): 1 dispatch each.

**Specific metrics to track**:

- **Required-script recall for `code_graph.py`** (the metric round-d
  measured at 8.3%): for the 8-eval E.2 subset, current `evals.json`
  marks `code_graph.py` as required on **4 ws evals — 028, 089, 107,
  108** (not on 041, 087, 105, or 118). Recall = `expected_called` /
  `expected_total`, so the denominator is 4, not 8. **Target: required-
  script recall ≥40% (≥2/4 of those evals invoke `code_graph.py`);
  aspirational target 100% (4/4)**. Round-d's 1/12 = 8.3% used the
  full-eval-set denominator from `script_call_confusion.csv`; the
  per-subset recall is the cleaner round-e measurement.
- **Total ws utilization** (separate metric, tracked alongside recall but
  not gated on): `n_runs_invoking` for `code_graph.py` across all ws
  runs in the subset. Round-d had 3/16. Useful as a directional signal
  for whether the bundled-script CLI examples are converting reading →
  executing on evals where the script wasn't strictly expected. bs
  invocation rate should remain near 0/N regardless of subset size.
- Eval-108 ws response: contains a source-verified metadata chain
  through `SortGroup.SortGroupElectrode * Electrode * BrainRegion` (or
  equivalent walk via `ElectrodeGroup`) that produces concrete
  sort-group keys. Either restriction-then-fetch (`(... & 'region_name
  LIKE "%CA1%"').fetch("sort_group_id")`) or restriction-then-pass-keys
  (`(... & BrainRegion_restricted).proj("sort_group_id")`) is acceptable;
  what's not acceptable is the round-d ws punt (*"I don't know your
  specific schema for that — happy to help wire it up if you tell me where
  region info lives in your DB"*) which leaves the derivation unspecified.
- Eval-118 ws response: contains qualitative-direction language ("fewer
  state bins", "faster compute", "lower spatial resolution", or
  equivalent). Round-d's response walked the cascade structure but did
  not name the qualitative direction.
- Eval-087 ws response: contains qualitative-direction language for the
  position-params swap (more rows, finer/coarser, etc.).

**ws-only vs. ws+bs question**: For the behavioral-change measurements,
ws-only is sufficient (we're measuring whether the refinements changed
ws agents). bs scores should not move and re-grading round-d's existing
bs transcripts in Phase E.1 already gives us the bs baseline. Halving
dispatch cost in this phase if we go ws-only.

**Success criteria**:

- `code_graph.py` recall ≥ 40%.
- Eval-108 ws response derives hippocampal sort_group_ids via metadata join
  (does not punt).
- Eval-118 + 087 ws responses name the qualitative direction.
- Eval-107 + 041 ws scores hold (regression check).

**If required-script recall is 0/4** (i.e. no ws agent on 028, 089, 107, or
108 invoked `code_graph.py` despite the new CLI examples in those evals'
loaded references): the CLI examples didn't convert reading → executing.
Either (a) make the directive more imperative, (b) add a worked example
showing the script's output verbatim, OR (c) accept that LLM agents prefer
manual source-walks over scripts and remove the script-execution claim from
the skill's value proposition. With a 4-eval denominator the recall scale is
discrete (0 / 25% / 50% / 75% / 100%), so 0/4 is the only "no signal"
outcome; 1/4 = 25% is *some* conversion.

## Phase E.3 — `destructive_operations.md` content audit

**Goal**: Determine whether the reference is content-bottlenecked or whether
the round-d failures were all rubric-friction. No eval-running cost; just
reading + analysis.

**Inputs**:

- 4 round-d evals where `destructive_operations.md` was loaded but ws still
  failed: **085, 087, 088, 118** (per round-d's
  [`reference_effectiveness.csv`](https://github.com/edeno/spyglass-skill-workspace/blob/main/runs/round-d-2026-04-30/summary/data/reference_effectiveness.csv)).
- For each: read the `response.md` + `grading.json` + the loaded
  `destructive_operations.md` sections. Identify what the response was
  missing that the reference *should* have provided.

**Sequencing note**: run E.3 *after* E.1 finishes. If E.1's re-grade
confirms 085, 087, 088 were mostly rubric-friction (085/088 lifted toward
~7/8 and 087 toward ~14/15 under the corrected rubric per the E.1 per-eval
table), the audit narrows to **118 plus any genuinely residual destructive-op
miss surfaced by the re-grade**. The decision tree below already handles
this case (the "rubric-friction" branch closes those evals out), but
flagging here so the analysis effort scales to where the real content gap
actually lives.

**Decision tree**:

- **If the gaps are rubric-friction** (literal filename substrings,
  compound assertions): no reference content fix needed; the rubric
  corrections from round-d already address these. Document and close.
- **If the gaps are missing worked examples**: add per-trap worked
  examples to `destructive_operations.md` (e.g., a paired-shape example
  for each common destructive helper, alongside the existing `## Required
  workflow` checklist).
- **If the gaps are reference-organization** (right content present but
  buried under wrong heading, missing TOC entry, missing cross-link):
  reorganize without adding new content.
- **If the gaps are missing concepts** (e.g., the response needed
  `merge_delete` semantics that the reference doesn't cover): add
  targeted content.

**Success criterion**: a writeup naming each of the 4 failed evals and
classifying the gap into one of the four buckets above. The writeup is the
deliverable; content edits (if any) land as a separate small PR before the
full sweep.

## Phase E.4 — Full 130-eval sweep (gated)

**Decision gate**: only run if Phases E.1, E.2, E.3 confirm:

- Rubric corrections lifted scores as predicted (E.1).
- Refinements changed agent behavior on targeted evals (E.2).
- `destructive_operations.md` audit identified gaps OR confirmed no
  content fix needed (E.3).

If any phase says "the fix didn't work as expected": investigate before
spending the full-sweep budget.

**Cost**: ~$200, ~8M tokens, full round-c-style 7-batch dispatch (~130
evals × 2 conditions = 260 dispatches + grading).

**Goals**:

- **Headline**: ws full-pass rate vs. round-c (round-c was 85.4%). Lift
  expected from rubric corrections + 6 refinements + bundled-script CLI
  examples + the 22 reference-precision fixes shipped in PR #26.
- **Regression check**: ws-worse-than-bs case count vs. round-c. Round-c
  had 3; round-d had 4 in narrow rerun (all rubric-corrected). Target:
  ≤2 after corrections take effect.
- **Saturated-tie audit**: confirm that round-d's saturated-tie evals
  (029, 072, 099, 100) remain saturated — no regression from the new
  edits.
- **Statistical significance**: McNemar should be powered enough at n≈130
  to give p<0.05 on the headline if the round-d-narrow Δ holds (round-d
  Δ +12.5pp full-pass; expected discordant pair count at full scale ≈
  20-40 vs round-d's 4).

## Open methodological questions (capture, do not block round-E)

- **Statistical power planning**: what discordant-pair count do we expect at
  130 evals × the round-d effect size? Round-d's n=4 was underpowered
  (p=0.625); a back-of-envelope at the same effect rate would predict ~30
  discordant pairs at full scale. Worth running a simple power calculation
  before Phase E.4 commits.
- **bs script-access policy**: round-d forbade bs from invoking
  `skills/spyglass/scripts/`. Round-c allowed it implicitly. Round-d's
  stricter policy is the cleaner comparison shape but is a methodology
  choice worth documenting in `dispatch_prompts.md` as the canonical
  decision.
- **"Skill changed problem-solving shape" measurement**: round-d's
  `mean_refs_per_outcome` from
  [`transcript_stats.json`](https://github.com/edeno/spyglass-skill-workspace/blob/main/runs/round-d-2026-04-30/summary/data/transcript_stats.json)
  was the proxy, but the round-c-vs-round-d comparison didn't replicate
  cleanly (round-c ws_fail > ws_pass on refs opened; round-d had them
  ~equal). A sharper proxy would help round-E narrate behavioral change
  beyond pass/fail.

## Out of scope for round-E (queue for round-F or beyond)

- **Eval-set coverage expansion**: round-d's narrow rerun was Phase-2-driven.
  Round-F should add metadata-derivation and trap-recognition cohorts to
  the full eval set. Skill's competitive edge over training+source is on
  knowledge NOT in source — anti-pattern recognition, workflow shapes,
  trap avoidance — and the current eval set undersamples these.
- **"Skill light-touch" mode**: round-d's `both_pass` evals (29, 72, 99,
  100) ate 27% of the skill's extra-token spend on questions where bs got
  the answer alone. A routing gate that detects "this is an easy
  dependency-tracing prompt — short-circuit" would save tokens without
  hurting quality, but designing it correctly requires a coverage study
  of which question shapes are saturated vs. discriminating. Defer.
- **Reference-content audits beyond `destructive_operations.md`**: per
  `reference_effectiveness.csv`, several other references have <50%
  pass-rate-when-loaded. If the round-E full sweep confirms the
  destructive_operations.md audit shape works, apply it to the next
  worst-performing reference in round-F.

## Methodology already locked in (recap from workspace README)

The round-d post-run workflow is now codified in
`spyglass-skill-workspace/README.md § Adding a new sweep`:

- **Step 0** — Pre-flight context probe (cheap insurance, ~$0.01).
- **Step 4** — Post-run rubric audit (mandatory before findings.md).
- **Step 5** — Path-cite discipline in narrative (every claim cites the
  specific summary CSV/JSON).
- **Step 6** — External reviewer pass before commit.

Round-E inherits these without further work; the methodology hardening is
not a phase, it's the baseline.

~4 hours wall-clock orchestration. Total budget if E.4 doesn't run:
**~$25-35**. The gating sequence is the cost-control mechanism.
